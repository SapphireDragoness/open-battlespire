# 3D models (*.3D)

The models for level geometry, furniture, items and weapons. They're stored
in `GAMEDATA/3D.BSA` (2,395 models), and the v1.5 patch adds loose `.3d`
files in `GAMEDATA/`. Of those loose files, 110 are byte-identical copies of
archive records, and 135 exist only loose (mostly the models for the
deathmatch levels `dmog`, `dmka` and `dmzr`). `GAMEDATA/3D.BS6` is an older
copy of the archive (2,115 records); the game only references `3d.bsa`.

This is Daggerfall's model format with one change: each face header is 10
bytes instead of 8, because the texture field is 32 bits.

Status: **verified**. All 2,395 models parse, every face vertex points at a
valid point, and every face texture resolves to an image
(`tests/test_install_data.c`). Models exported to glTF render correctly
(furniture upright, textures aligned), and placed in levels they join up
seamlessly. Level 1's layout matches the game's own automap (`MAP000.BSI`).

## Header (64 bytes)

| Offset | Type | Field |
|---|---|---|
| 0 | char[4] | version: `v2.7` (2,370 models) or `v2.6` (25) |
| 4 | i32 | point count |
| 8 | i32 | face count |
| 12 | u32 | radius: the largest distance of any point from the origin (all models) |
| 16 | 8 bytes | unknown; the u32 at 20 is non-zero in 1,837 models |
| 24 | i32 | offset of the plane data |
| 28 | i32 | offset of the object data |
| 32 | i32 | object data count |
| 36 | 12 bytes | always 0 |
| 48 | i32 | offset of the point list (always 64) |
| 52 | i32 | offset of the normal list |
| 56 | i32 | always 0 |
| 60 | i32 | offset of the face list |

The sections don't always come in the same order (in a few models the
normals come before the faces), so always use the offsets.

## Points

`point count` × `{ i32 x, y, z }`. Units: **256 model units = 1 level
unit** (inferred: this scale makes placed models meet in all campaign
levels). **+y points down**, as in Daggerfall: table tops, bench seats and
anvils face −y.

## Normals

`face count` × `{ i32 x, y, z }` with **256 = 1.0**. Each face's vertices wind
counter-clockwise around its normal (right-hand rule); this holds for every
face with three or more distinct vertices.

## Faces

```
u8  vertex_count
u8  light              self-illumination in shade levels (0 for most faces), see below
u32 texture            see below
u32 zero               always 0
vertex_count x {
    u32 point_offset   byte offset into the point list (a multiple of 12)
    i16 u, v           texture coordinates, see below
}
```

Faces are convex polygons; a triangle fan triangulates them.

### Light byte

Values: 0 (70,503 faces), 6 (29,584), 15 (26,897), and 5..63. It's the face's
**self-illumination, in half shade levels**, added to the level's ambient and
to the lights before the shade level is capped at 31 (the rasteriser uses
`byte << 8`, and one level is 512). Measured against the original in level 1:

| Face | Byte | Levels it adds |
|---|---|---|
| wall | 45 | about 21.6 |
| battlemage | 6 | about 2.8 |
| waterfall | 60 | full brightness |

The full rule is in `docs/re/README.md` (lighting).

### Texture

| Value | Meaning | Faces |
|---|---|---|
| < 40⁶ | **BSI image name packed in base 40**: six characters, most significant first, each `0–9` = 0–9, `A–Z` = 10–35, `_` = 37, and 39 = padding at the end. `0xB33E66C0` = `TERR00`, `0x455B6B7F` = `BELL` | 133,821 |
| `0xFFFFxxxx` | solid colour; the low 16 bits are probably encoded like BSI `HICL` entries (RGB555 shifted left one bit; inferred) | 67 |
| `0xFFFFFFFE` | invisible: not drawn. Probably collision or trigger surfaces | 866 |

The image is `<name>.BSI` in `BSI.BSA`. A few names don't match a file
exactly:
- Names longer than six characters are cut short (`STRUT0` for `STRUT01.BSI`,
  `KEYHOL` for `KEYHOLE3.BSI`).
- `HAND00`–`HAND09` refer to the single image `HAND.BSI`.

`bs_assets_texture()` resolves those by prefix and then by dropping trailing
digits. How the game itself resolves them isn't confirmed.

### Texture coordinates

Units are **1/16 texel**. A face spanning a whole 128-pixel texture has a
span of 2048.

Only the first three vertices store usable values:
- vertex 0: absolute (u, v);
- vertices 1 and 2: deltas from the previous vertex;
- vertices 3 and up: the stored values are leftovers. Compute each one from
  the face plane: write the point as `p0 + s·(p1 − p0) + t·(p2 − p0)` and
  apply the same `s`, `t` to the UVs.

This matches Daggerfall Unity's handling of v2.7 models. Checked on all
quads: the derived UVs give clean rectangles and trapezoids, and textures
line up across neighbouring faces.

## Plane data and object data

- **Plane data:** 24 bytes per face in `v2.7` (all zero in 1,818 models).
  The `v2.6` layout differs.
- **Object data:** `object data count` records, each with an i32 position, a
  count, and a list of (face offset, u16) pairs.

Neither is needed for drawing. Daggerfall's documentation lists them as
unknown too; they may be used for collision or visibility.

## Tools

```sh
bstool model                       # summary of every model in 3D.BSA
bstool model -o out/ table chair   # export models as glTF (+ PNG textures)
```
